# 视频刮削逻辑重构计划

## 一、当前问题分析

### 核心瓶颈：`VideoService` 是一个 1718 行的 God Class

当前刮削流程完全串行，且所有操作都在 `DatabaseWriteLock` 写锁内执行：

```
scanDirectory（持有写锁）
  └─ 每个视频文件：
       └─ extractAndSaveMetadata（持有写锁）
            ├─ 读取本地 NFO
            ├─ ffprobe 分析（进程调用，耗时）
            ├─ DB 写入
            └─ 推断 mediaType → DB 写入

autoScrapeAll（异步，但内部串行）
  └─ 每个视频：
       └─ scrapeAndBindTmdb（持有写锁）
            ├─ TMDB API 搜索（网络 I/O）
            ├─ TMDB API 获取详情（网络 I/O）
            ├─ DB 写入（更新元数据）
            ├─ 重命名文件（文件 I/O）
            ├─ 移动文件到元数据目录（文件 I/O）
            ├─ 生成 NFO（文件 I/O）
            ├─ 下载海报+背景图（网络 I/O）
            └─ 保存演员+下载头像（网络 I/O + DB 写入）
```

### 问题总结

| 问题 | 影响 |
|------|------|
| 写锁内做网络 I/O | TMDB API 调用、图片下载期间阻塞所有 DB 写入 |
| 写锁内做文件 I/O | 文件移动/重命名期间阻塞所有 DB 写入 |
| 每个视频单独 `repository.save()` | N 个视频 = N 次 DB 事务 |
| `VideoService` 承担所有职责 | 难以维护、测试、扩展 |
| 无批量操作 | 大量视频时性能差 |
| `rescrapeByLibrary` 全量解绑+全量扫描 | 不必要的重复工作 |

---

## 二、重构目标

1. **最小化写锁持有时间**：只在必要时持有写锁，I/O 操作完全并发
2. **拆分职责**：将 `VideoService` 拆分为专注的 Service
3. **批量操作**：使用 `saveAll()` 减少 DB 事务次数
4. **流水线化**：将刮削拆分为可独立执行的阶段
5. **保持 API 兼容**：Controller 层接口不变

---

## 三、新架构设计

### 3.1 Service 拆分

| 新 Service | 职责 | 原 VideoService 方法 |
|------------|------|---------------------|
| `VideoScanService` | 扫描发现视频、提取基础元数据 | `scanDirectory`, `extractAndSaveMetadata` |
| `VideoScrapeService` | TMDB 搜索、匹配、绑定元数据 | `autoScrapeAll`, `tryScrapeVideo`, `scrapeAndBindTmdb`, `searchFromTmdb`, `pickBestTmdbMatch` |
| `VideoOrganizeService` | 文件重命名、移动、目录整理 | `organizeVideos`, `moveVideoToMetadataDir`, `renameVideoFile` |
| `VideoAssetService` | NFO 生成、封面下载、演员图片 | `generateNfoAndCovers`, `downloadSeriesCovers`, `saveActors` |
| `VideoService`（保留） | 对外 API 门面、组合调用 | 公共查询方法、组合流程 |

### 3.2 流水线阶段

### 3.3 关键设计：写锁最小化

**核心原则**：I/O 操作（网络、文件系统）在写锁外执行，只在 DB 批量写入时短暂持有写锁。

```java
// 旧模式（所有操作都在写锁内）
DatabaseWriteLock.lock();
try {
    for (Video video : videos) {
        tmdbService.search(query);      // 网络 I/O，阻塞其他写入
        tmdbService.getDetail(id);      // 网络 I/O
        repository.save(video);         // DB 写入
        Files.move(...);                // 文件 I/O
        coverArtService.download(...);  // 网络 I/O
    }
} finally {
    DatabaseWriteLock.unlock();
}

// 新模式（只在 DB 写入时持有写锁）
// Phase 5: TMDB 搜索（无锁，可并发）
List<ScrapeResult> results = videos.parallelStream()
    .map(v -> tmdbService.searchAndMatch(v))
    .toList();

// Phase 6: 批量绑定（单次写锁）
DatabaseWriteLock.runInWriteLock(() -> {
    List<Video> updates = results.stream().map(r -> {
        r.video.setTmdbId(r.match.getId());
        return r.video;
    }).toList();
    videoRepository.saveAll(updates);
});
```

### 3.4 批量操作示例

```java
// 旧模式：每个视频单独保存
for (Video video : videoFiles) {
    DatabaseWriteLock.runInWriteLock(() -> {
        repository.save(extractAndSaveMetadata(path));
    });
}

// 新模式：批量保存
List<Video> toSave = videoFiles.stream()
    .map(this::extractMetadata)  // 纯内存操作
    .toList();
DatabaseWriteLock.runInWriteLock(() -> {
    videoRepository.saveAll(toSave);
});
```

## 五、详细实现步骤

### Step 1: 新建 `VideoScanService`

从 `VideoService` 抽取：
- `scanDirectory()` — 目录扫描逻辑
- `extractAndSaveMetadata()` — 基础元数据提取
- `parseSeasonEpisode()` — 集数解析
- `cleanTitleForSearch()` — 标题清洗
- `SUPPORTED_FORMATS` 等常量
- `SE_EP_PATTERN` 等正则

关键改动：
- `extractAndSaveMetadata` 改为纯内存操作，返回 `Video` 对象而非直接写 DB
- 新增 `batchExtractAndSave(List<Path> paths, Long libraryId)` 批量版本
- ffprobe 分析移到独立方法，可并发调用

### Step 2: 新建 `VideoScrapeService`

从 `VideoService` 抽取：
- `autoScrapeAll()` — 自动刮削入口
- `tryScrapeVideo()` — 单个视频刮削
- `scrapeAndBindTmdb()` / `doScrapeAndBind()` — TMDB 绑定
- `searchFromTmdb()` — TMDB 搜索
- `pickBestTmdbMatch()` — 最佳匹配选择
- `rescrapeVideo()` — 重新刮削
- `rescrapeByLibrary()` — 按库重新刮削
- `unbindTmdb()` / `unbindByTmdbId()` — 解绑
- `updateVideoFromMovieDetail()` / `updateVideoFromTvDetail()` — 元数据更新

关键改动：
- `doScrapeAndBind` 拆分为：
  1. `fetchTmdbMetadata()` — 纯 API 调用，返回 metadata 对象
  2. `applyTmdbMetadata()` — 纯内存更新 Video 对象
  3. `saveTmdbBinding()` — DB 写入（在写锁内）
- TMDB 搜索可并发执行
- 图片下载移到 VideoAssetService

### Step 3: 新建 `VideoOrganizeService`

从 `VideoService` 抽取：
- `organizeVideos()` — 批量整理
- `moveVideoToMetadataDir()` — 移动视频
- `renameVideoFile()` — 重命名文件
- `generateCleanFileName()` — 生成干净文件名
- `moveAssociatedFile()` / `moveAssociatedSubtitles()` — 移动关联文件
- `renameAssociatedFile()` / `renameAssociatedSubtitles()` — 重命名关联文件
- `renamePosterFanartByPattern()` — 重命名封面

关键改动：
- 所有方法改为接收 `Video` 对象而非从 DB 查询
- 文件操作在写锁外执行
- 新增 `batchOrganize(List<Video> videos)` 批量版本

### Step 4: 新建 `VideoAssetService`

从 `VideoService` 抽取：
- `generateNfoAndCovers()` — NFO + 封面生成
- `downloadSeriesCovers()` — 系列封面下载
- `downloadCoverImage()` — 单张封面下载
- `saveActors()` — 保存演员 + 下载头像
- `saveOneActor()` — 单个演员保存
- `getActorsDir()` / `findSeasonDir()` — 目录查找
- `cleanupUnboundFiles()` / `cleanupUnboundActors()` — 清理

关键改动：
- 所有方法在写锁外执行
- 封面下载可并发
- 演员图片下载可并发

### Step 5: 新建 `VideoPipelineService`

流水线编排，组合所有阶段：

```java
@Service
@RequiredArgsConstructor
public class VideoPipelineService {
    private final VideoScanService scanService;
    private final VideoScrapeService scrapeService;
    private final VideoOrganizeService organizeService;
    private final VideoAssetService assetService;
    private final ScrapeProgressService progressService;

    /**
     * 完整流水线：扫描 → 刮削 → 整理 → 资产生成
     */
    public void runFullPipeline(String directoryPath, Long libraryId) {
        // Phase 1-2: 扫描 + 批量入库
        List<Video> videos = scanService.scanAndSave(directoryPath, libraryId);

        // Phase 3-4: 媒体信息分析
        scanService.batchAnalyzeMediaInfo(videos);

        // Phase 5-6: TMDB 刮削
        scrapeService.batchScrapeAndBind(videos);

        // Phase 7: 文件整理
        organizeService.batchOrganize(videos);

        // Phase 8: 资产生成
        assetService.batchGenerateAssets(videos);
    }

    /**
     * 仅刮削（不整理文件）
     */
    public void runScrapeOnly(Long libraryId) {
        List<Video> videos = scrapeService.findUnscraped(libraryId);
        scrapeService.batchScrapeAndBind(videos);
        assetService.batchGenerateAssets(videos);
    }

    /**
     * 仅整理（不刮削）
     */
    public void runOrganizeOnly(String path) {
        List<Video> videos = scanService.findByPath(path);
        organizeService.batchOrganize(videos);
    }
}
```

### Step 6: 瘦身 `VideoService`

保留为 API 门面：
- 所有查询方法（`getAllVideos`, `getVideoById`, `searchByTitle` 等）
- 收藏/进度等用户状态方法
- 流方法（`streamVideo`）
- 组合调用各 Service 的公共方法
- 删除所有已抽取的私有方法

### Step 7: 更新 `VideoController`

- 注入 `VideoPipelineService` 替代直接调用 `VideoService`
- `scan` 端点调用 `pipelineService.runFullPipeline()`
- `rescrape` 端点调用 `scrapeService.batchScrapeAndBind()`
- `organize` 端点调用 `organizeService.batchOrganize()`
- 保持现有 API 路径和响应格式不变

## 七、风险控制

1. **API 兼容性**：Controller 层接口不变，前端无感知
2. **数据安全**：批量操作使用事务，失败可回滚
3. **渐进式迁移**：先建新 Service，再迁移方法，最后删除旧代码
4. **回退方案**：保留原 VideoService 方法签名，通过委托保持兼容
